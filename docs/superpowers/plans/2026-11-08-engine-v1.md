# Engine v1 (playlist / Saved → new Spotify playlist): Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A user brings their own Spotify Client ID and logs in. They pick one of their playlists or their Saved tracks and describe the set with a form. The app selects matching tracks (mood + genre + sound), orders them, plans a cut per track, and creates a **new** private Spotify playlist. It also reports data coverage, which is the go/no-go check for Phase 0 (γ).

**Architecture:** A static React app (existing Vite + TS code). All mix logic is pure TypeScript in `src/mix/` and unit-tested. A small Cloudflare Worker in `worker/` keeps the Last.fm key and proxies Deezer. All user data stays in the browser (localStorage).

**Tech Stack:** React 19, TypeScript, Vite, Vitest (+ happy-dom for storage tests), Cloudflare Workers (wrangler), Spotify Web API (Dev Mode, Feb 2026 paths), ReccoBeats, Deezer, Last.fm.

**Spec:** `docs/superpowers/specs/2026-11-08-spotify-mix-design.md`

**Out of scope here (separate plans after this one):**
- Phase 2: set player with cuts (Connect + SDK, timing check δ), user cue corrections, and LRCLIB lyric-based chorus detection. These need the player so they can be checked by ear.
- Phase 3: free-text prompt via Workers AI and the "whole Spotify" source (check β).
- Phase 4: more genres.
- Deezer-preview analysis (spec §5.3.4): only if Task 10 shows coverage < 80%.

## Global Constraints

- Never modify any existing playlist or library item of the user. The only writes are `POST /me/playlists` and `POST /playlists/{id}/items` on the playlist we just created.
- Use Feb 2026 Dev Mode paths: `/playlists/{id}/items` (never `/tracks`), `POST /me/playlists`, search `limit` ≤ 10. Batch `GET /artists?ids=` is removed, so use `GET /artists/{id}`, one request per artist, cached. `GET /me` no longer returns `product`.
- The playlist item field is `item` (2026). Keep accepting `track` too.
- Never two tracks at once (no overlap). This matters in Phase 2, but no code here may assume overlap.
- A track enters a set only if it passes **all three**: mood, genre, sound. "Enough data" = BPM present **and** at least one genre signal (Last.fm tag or Spotify artist genre). Tracks without enough data are excluded by default and listed with a reason.
- Phase 0 coverage go threshold: **≥ 80%** of source tracks with BPM **and** a genre signal.
- Cuts start and end on phrase boundaries (16-bar grid). Minimum segment 64 bars. Bar = 240 / BPM s.
- Never pad a set with non-matching tracks. If the source is too small, report the shortfall.
- "Not found" feature results expire after **3 days**. They are never cached permanently.
- UI language: Greek.
- No secrets in the browser bundle. The Last.fm key lives only in the Worker (`LASTFM_API_KEY` secret).

## Review Focus

1. **Spotify 429 rate limit** while loading a 500+ track playlist plus per-artist calls: expect a wait of `Retry-After` seconds and then continuation, never a crash. Test: Task 2 `retries after 429 using Retry-After`.
2. **Playlist rows with `null` item, local files, episodes, or `id: null`**: expect them to be skipped silently. Test: Task 2 `skips null, local and non-track items`.
3. **The same song twice** (same id, or same ISRC on different releases): expect it to appear once in a set. Test: Task 7 `dedupes by id and by isrc`.
4. **Source too small for the requested duration**: expect a set with what fits, plus `shortfallMin > 0`, and no padding. Test: Task 9 `reports shortfall instead of padding`.
5. **Created playlist with more than 100 tracks**: expect items added in chunks of 100, in order. Test: Task 2 `adds items in chunks of 100 in order`.

### Task 7: Selection (three-gate filter)

**Files:**
- Create: `src/mix/select.ts`
- Test: `src/mix/select.test.ts`

**Interfaces:**
- Consumes: `TrackProfile` (Task 5), `SetSpec`, `GenreProfile` (Task 6).
- Produces:
```ts
export type ExcludeReason = "no-data" | "bpm" | "mood" | "genre" | "sound" | "duplicate";
export interface Scored { profile: TrackProfile; mood: number; genre: number; sound: number; total: number }
export interface Selection { passed: Scored[]; excluded: { profile: TrackProfile; reason: ExcludeReason }[] }
export function scoreTrack(p: TrackProfile, spec: SetSpec, g?: GenreProfile): Scored;
export function selectTracks(profiles: TrackProfile[], spec: SetSpec, g?: GenreProfile): Selection;
```
- Gates, checked in this order (the first failure becomes the reason): duplicate (same `track.id`, or same non-null `isrc`, as an earlier profile) → `no-data` (`!hasEnoughData`) → `bpm` (`features.bpm` outside `spec.bpm`) → `mood` < 0.5 → `genre` < 0.6 → `sound` < 0.5.
- `mood` = 1 − mean of available terms: `max(0, |energy − spec.energy| − spec.wave) / 0.4` and `|valence − spec.valence| / 0.5` (each clamped to 0..1). A missing feature contributes 0.3. If both features are missing, the score is 0.4, so the track fails.
- `genre` = max over the track's tags: 1 if the tag ∈ `spec.genres`; 0.6 if `genreFamily(tag)` equals the family of any spec genre; else 0.
- `sound`: if the vocals rule fails → 0. Rules: `"none"` requires the `"instrumental"` sound tag; `"some"` rejects instrumentalness < 0.2 **only** when the track has no `"vocal"` tag either; `"any"` always passes. Otherwise, if `spec.soundTags` is empty → 1. Else the share of spec sound words found in `profile.soundTags` (case-insensitive substring), mapped as: 0 matches → 0, ≥ 1 match → `0.5 + 0.5 × share`.
- `total` = `mood + genre + sound`. `passed` is sorted by `total` desc.

- Test: `src/mix/order.test.ts`

**Interfaces:**
- Consumes: `Scored` (Task 7), `SetSpec`, `GenreProfile`.
- Produces:
```ts
export function camelotDistance(a: string | null, b: string | null): 0 | 0.3 | 0.5 | 1;
export function bpmCost(a: number, b: number, tolerance: number): number;
export function energyTarget(index: number, spec: SetSpec): number;
export function transitionCost(a: TrackProfile, b: TrackProfile, g?: GenreProfile): number;
export function pathCost(order: TrackProfile[], spec: SetSpec, g?: GenreProfile): number;
export function orderTracks(items: TrackProfile[], spec: SetSpec, g?: GenreProfile): TrackProfile[];
```
- `camelotDistance`: same code → 0. Same letter with numbers ±1 (12↔1 wraps), or same number with A↔B → 0.3. Either null → 0.5. Else 1.
- `bpmCost`: d = |a − b| / min(a, b). d ≤ 0.02 → 0. 0.02 < d ≤ tolerance → linear 0..1. d > tolerance → 3.
- `energyTarget(i)` = `spec.energy + spec.wave × sin(2π·i / 8)`.
- `transitionCost` = `bpmCost + camelotDistance`.
- `pathCost` = Σ transitionCost + 2 × Σ |energy_i − energyTarget(i)| (missing energy → 0.2 per position).
- `orderTracks`: start with the track whose BPM is lowest among those with energy within 0.1 of `energyTarget(0)` (else the lowest BPM). Greedy nearest neighbour by `transitionCost + 2·|energy − energyTarget(next index)|`. Then 2-opt on `pathCost` until no improvement, with a cap of 2 s wall time (`performance.now()`). 0 or 1 items → return as is.

### Task 9: Set plan (duration fill, cuts by role, shortfall)

**Files:**
- Create: `src/mix/plan.ts`
- Modify: `src/mix/music.ts` (`planSegment` accepts `mode: SegmentMode` unchanged; export `GRID_BARS`, `SEGMENT_BARS`)
- Test: `src/mix/plan.test.ts`

**Interfaces:**
- Consumes: `selectTracks` (7), `orderTracks` / `transitionCost` (8), `planSegment` (music.ts).
- Produces:
```ts
export type Role = "main" | "bridge";
export interface SetItem { profile: TrackProfile; segment: Segment; role: Role }
export interface SetPlan { spec: SetSpec; items: SetItem[]; totalSec: number; shortfallMin: number; selection: Selection; coverage: Coverage }
export interface Coverage { total: number; withBpm: number; withGenre: number; enough: number; enoughPct: number; go: boolean } // go = enoughPct >= 80
export function computeCoverage(profiles: TrackProfile[]): Coverage;
export function planSet(profiles: TrackProfile[], spec: SetSpec, g?: GenreProfile): SetPlan;
```
- Algorithm:
  1. `selectTracks`. Take `passed` in `total` order, adding each track's estimated segment length (`planSegment` with `spec.cutStyle`), until the sum ≥ `durationMin × 60`.
  2. `orderTracks` on the taken tracks.
  3. Role: `bridge` if `transitionCost` to the previous **or** next track is > 1.5, else `main`. Segment: `cutStyle === "full"` → whole track for every role. Otherwise main → `planSegment(cutStyle)`, bridge → `planSegment("fast")`.
  4. `totalSec` = Σ segment lengths. `shortfallMin` = `max(0, ceil((durationMin×60 − totalSec)/60))`. Never add tracks that failed selection.
